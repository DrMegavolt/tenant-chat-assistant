# 0005 — Tenant-qualified append-only conversations

- **Status:** Accepted
- **Date:** 2026-08-02

## Context

A composite foreign key prevents cross-tenant relationships, but it does not
stop an adapter from reading or updating a known UUID without a tenant filter.
Client-supplied transcript snapshots also permit replacement, reordering, and
lost updates.

## Decision

Persist conversations through async PostgreSQL adapters. Every read, lock,
update, and delete predicate includes both tenant ID and record ID. Missing and
wrong-tenant records return the same domain error.

Conversation and message IDs are generated by the server. The public contract
can create a conversation, append one message, or read committed history; it
cannot replace or reorder prior messages.

Appending a message locks the tenant-qualified conversation row, uses its
monotonic version as the next sequence, inserts the message, and increments the
version in one transaction. A unique tenant/session/sequence constraint protects
the final ordering invariant.

Production composition uses PostgreSQL stores. In-memory stores are explicit
test doubles, not a runtime fallback.

## Consequences

Replicas share committed state, restarts preserve conversations, cross-tenant
UUID knowledge is insufficient for access, and concurrent writes to one
conversation receive a deterministic order.

Writers to the same conversation are deliberately serialized. Database pool
capacity must account for every API and worker process.

## Alternatives considered

- **Optimistic updates with retries:** viable, but more complex for naturally
  sequential conversations.
- **A database sequence per conversation:** rejected because it creates schema
  objects with session lifecycle.
- **Advisory locks:** rejected because their keys are easier to misuse and are
  not tied to relational constraints.
